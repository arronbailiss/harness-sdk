`programmatic_tool_caller` lets the model use its other tools by writing a short program,
instead of calling them one at a time and waiting for each result. It is on by default.

## How it works

The model calls the tool with a `code` string of Python. That code runs in isolation with every other
registered tool exposed as an async function, so the model can chain calls, loop over them,
filter results, and run independent calls in parallel, all in a single turn. Only text the
code sends to `print` returns to the model; a tool's
return value stays in the code's local scope unless the code prints it. That is the point:
a step that touches many tools produces one concise result rather than filling the
conversation with every intermediate payload.

For example, the model can read several files, keep only the matches it cares about, and
print a summary, without the full contents of each file ever entering the context window.

## Interventions still apply

The tool calls the code makes run through the agent's normal executor, so an autonomous
[intervention](../../configure/interventions/) policy (a Cedar policy or a
natural-language risk policy) that denies a call blocks it, and the code sees a catchable
error. Interrupt-based human approval cannot prompt from inside the code, so a call gated
that way raises a catchable error rather than pausing for input.

## Isolated code execution

The code runs in [Monty](https://github.com/pydantic/monty), a Python interpreter that
isolates the code it runs. Filesystem, environment, network, and process access do not exist
in it, so the only thing model-authored code can reach is the set of tool functions handed
in.

:::caution[Isolation for the code, not the tools]
Monty bounds the code, not the tools it calls: `shell` still runs commands on the host. For
an OS boundary around the tools themselves, run the agent inside a Strands Harness SDK
[sandbox](../../../sdk/sandbox/).
:::

Output is capped (a runaway print cannot blow up the context window), and awaited code is
bounded by a default timeout.

  <Tab label="Rust">
    Install the worker version that matches the crate:

    ```bash
    cargo install monty-runtime --version 1.5.0 --locked
    ```

    The harness finds it through `MONTY_BIN`, `PATH`, or the running application's
    Cargo workspace. Set `MONTY_BIN` when you want to pin the exact binary:

    ```bash
    export MONTY_BIN="$(command -v monty)"
    ```

    Worker execution needs the `monty-pool` Cargo feature, which default features
    include. If you disable default features, include `monty-pool` with the model
    provider and every other optional capability your application uses:

    ```bash
    cargo add strands-harness --no-default-features \
      --features openai,mcp,cedar,monty-pool
    ```

    To choose a worker path in code, replace the built-in caller with one configured
    for that binary. The lower-level API exposes
    [`ProgrammaticToolCaller`](https://docs.rs/strands-harness/latest/strands_harness/tools/programmatic_tool_caller/struct.ProgrammaticToolCaller.html),
    [`ProgrammaticToolCallerConfig`](https://docs.rs/strands-harness/latest/strands_harness/tools/programmatic_tool_caller/struct.ProgrammaticToolCallerConfig.html),
    and
    [`Isolation`](https://docs.rs/strands-harness/latest/strands_harness/tools/programmatic_tool_caller/enum.Isolation.html):

    ```rust
    --8<-- "user-guide/harness/tools/programmatic-tool-calling.rs:worker"
    ```

    Without `monty-pool` or a worker binary, the interpreter runs in process. That
    mode keeps the Python subset and per-step limits, but it cannot enforce a hard
    total-memory cap or isolate an interpreter crash from the agent process.
  </Tab>
</Tabs>

## Selecting it

The built-in-tools option selects this tool by name. Remove
`programmatic_tool_caller` from the list to turn it off; see
[add tools and instructions](../../configure/tools-and-instructions/) for
how selection works.
