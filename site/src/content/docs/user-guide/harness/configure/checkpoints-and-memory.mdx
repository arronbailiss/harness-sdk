Strands harness has two independent ways to remember, and they answer different questions.
A **session** (checkpoint) persists one conversation so you can resume that exact task
after a restart. **Long-term memory** distills durable facts and recalls them across
every conversation, whether or not a session is involved. They are orthogonal: you can
run with neither, either, or both.

Out of the box Strands harness keeps **sessions on** and **memory on**, so a fresh agent
already carries knowledge between unrelated runs, but does not resume a specific
conversation until you give it a session id.

## Which do you need?

| You want to… | Use | How |
| --- | --- | --- |
| Resume a task after a restart | A **session** | Set a session id |
| Carry facts, preferences, or decisions across unrelated runs | **Long-term memory** | On by default |
| Resume a task and retain knowledge | **Both** | Set an id; leave memory on |
| A one-shot task that should leave no trace | Neither | Disable sessions and memory |

The rest of this page is the detail behind that table, and the honest operational
answers (concurrency, isolation, deletion) for running either in production.

## Checkpoints: resume one conversation

A session persists a single conversation and replays it only when you resume that id.
Set a session id and Strands harness writes its state to disk, then rehydrates it
next time you build an agent with the same id:

<Tabs>
  <Tab label="Python">
    ```python
    from strands_harness import create_harness

    agent = create_harness(session={"id": "refactor-parser"})
    agent("Let's refactor the parser. Where should we start?")
    ```
  </Tab>
  <Tab label="TypeScript">
    ```typescript
    import { createHarness } from '@strands-agents/harness'

    const agent = await createHarness({ session: { id: 'refactor-parser' } })
    await agent.invoke("Let's refactor the parser. Where should we start?")
    ```
  </Tab>
  <Tab label="Rust">
    ```rust
    --8<-- "user-guide/harness/configure/checkpoints-and-memory.rs:session"
    ```
  </Tab>
</Tabs>

State is written under `./.agent/sessions`. Override it with
<Syntax
  py='session={"dir": ...}'
  ts="session: { dir }"
  rs="SessionConfig::builder().dir(...)"
/>.
Offloaded tool results from context management are kept there too, so a long task
survives restarts intact. To use a different backend, pass your own session manager
through to the agent. Your explicit manager wins over the one Strands harness builds
from `session`.

<Tabs>
  <Tab label="Python">
    The harness uses a `SnapshotSessionManager` backed by `LocalFileStorage` and
    restores the latest checkpoint during construction. The SDK also ships S3 storage.
  </Tab>
  <Tab label="TypeScript">
    The harness uses a `SessionManager` over file storage and restores the latest
    checkpoint during construction. The SDK also ships S3 storage.
  </Tab>
  <Tab label="Rust">
    The harness uses a `SessionManager` over file storage and restores the latest
    checkpoint during construction. Supply another `Storage` implementation for a
    different backend.
  </Tab>
</Tabs>

For the full option set see [persist sessions](../sessions/).
The Strands Harness SDK-level [session management](../../../sdk/agents/session-management/)
and [snapshots](../../../sdk/agents/snapshots/) pages cover immutable,
time-travel checkpoints and manual save/restore.

## Long-term memory: carry facts across conversations

Memory is on by default. Strands harness distills durable facts into files under
`./.agent/memory`, searches them before each user turn, and folds the top matches into
context, so knowledge survives across sessions and works with sessions off. The agent
also gets a `search_memory` tool for on-demand recall, and extraction runs in the
background every few turns on a small model, so keeping memory costs little.

Because memory persistence is plain files, independent of any session, it is the right
tool for preferences, project facts, and decisions that should outlive a single task.
For a stateless run, use
<Syntax py="memory=False" ts="memory: false" rs=".memory(false)" />.

To move the file store or replace it with custom stores:

<Tabs>
  <Tab label="Python">
    Use `memory={"dir": ...}` to move the default file store, or
    `memory={"stores": [...]}` to replace it.
  </Tab>
  <Tab label="TypeScript">
    Use `memory: { dir }` to move the default file store, or
    `memory: { stores }` to replace it.
  </Tab>
  <Tab label="Rust">
    Use `MemoryConfig::builder().dir(...).build()` to move the default file
    store. To replace it, construct `MemoryConfig` with the `stores` field set.
  </Tab>
</Tabs>

See
[give long-term memory](../memory/) and
the Strands Harness SDK's [memory overview](../../../sdk/memory/overview/).

:::note[They are not the same thing]
A session persists *one conversation*, replayed only when you resume its id. Memory
distills *durable facts* recalled across every conversation. Use a session to continue a
specific task; rely on memory to carry knowledge between unrelated runs.
:::

## Backends: what ships, and what doesn't

Both sessions and memory sit on the Strands Harness SDK's `Storage` abstraction. Each
SDK ships:

- `LocalFileStorage`: the default, with atomic writes (temp file + rename).
- `InMemoryStorage`: process memory for tests and short-lived agents.

A custom backend implements `write`, `read`, `delete`, and `list`, so sessions
or memory can use any store you operate.

<Tabs>
  <Tab label="Python">
    `S3Storage` supports production and multi-instance deployments. SQLite and
    PostgreSQL do not have first-party backends. Community integrations include
    [`strands-valkey-session-manager`](../../../../integrations/session-managers/strands-valkey-session-manager/)
    and
    [`AgentCoreMemorySessionManager`](../../../../integrations/session-managers/agentcore-memory/).
  </Tab>
  <Tab label="TypeScript">
    `S3Storage` supports production and multi-instance deployments. SQLite,
    PostgreSQL, Redis, and Valkey do not have first-party backends.
  </Tab>
  <Tab label="Rust">
    An S3 backend is not included. Supply a custom backend for remote or shared
    storage.
  </Tab>
</Tabs>

## Concurrency, isolation, and deletion

**Concurrency is single-writer.** Session management is designed around one live writer
per conversation. The built-in managers take no distributed lock, and the in-process
guard cannot see a writer running elsewhere, so overlapping invocations on the same
session id overwrite each other's turns and neither call errors. Session creation is a
check followed by a write, not an atomic operation, so two simultaneous cold starts on a
new id can both succeed. The later write wins, making this effectively
**last-write-wins**.
Run one writer per session id; if you fan out, add your own lock or route each id to a
single worker.

**Isolation is by namespace and scoped stores.** Each subsystem keeps its data under its
own namespace (the context manager's stash under `context/`, for example) so data never
collides, and long-term memory
supports a scoped store per tenant rather than one shared store. The session directory
is a trusted data store: restrict filesystem permissions to the agent process, and note
the Strands Harness SDK does not block symlinks inside it.

**Deletion.** Deleting a session removes its stored objects. Memory is plain files under
the memory directory, so removing a tenant's memory means deleting its directory or
store.

<Tabs>
  <Tab label="Python">
    File-backed deletion removes the session directory. S3-backed deletion removes every
    object under the session prefix and requires `s3:DeleteObject`.
  </Tab>
  <Tab label="TypeScript">
    File-backed deletion removes the session directory. S3-backed deletion removes every
    object under the session prefix and requires `s3:DeleteObject`.
  </Tab>
  <Tab label="Rust">
    File-backed deletion removes every object under the session storage prefix. A custom
    backend defines how that prefix is deleted.
  </Tab>
</Tabs>
