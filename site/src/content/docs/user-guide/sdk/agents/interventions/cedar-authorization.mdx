Cedar Authorization evaluates [Cedar](https://cedarpolicy.com) policies before each
tool call, giving you declarative, identity-aware access control over agent behavior.
It ships as a vended intervention handler.

## How it works

The handler sits at the tool-call boundary. When the agent attempts to invoke a tool, Cedar Authorization maps the call to a Cedar authorization request and evaluates your policies. If no `permit` statement matches, the tool call is denied and the agent receives feedback explaining the denial.

| Cedar concept | Maps to | Example |
|---|---|---|
| **Principal** | User identity | `User::"alice@acme.com"` |
| **Action** | Tool name | `Action::"search"` |
| **Resource** | Static (unconstrained) | `Resource::"agent"` |
| **Context.input** | Tool arguments | `{ query: "quarterly report" }` |
| **Context.session** | Invocation metadata | `{ hour_utc: 14, call_count: 3, role: "admin" }` |

The design is fail-closed: if principal identity cannot be resolved, all tool calls are denied.

Call counts persist with the agent's state and survive session reloads. Only
successful tool calls increment the counter. Counts are tracked per agent, so
when several agents share one handler, each has its own budget. By default,
agents created through delegation tools share the intervention handlers of the
agent that calls the tool. This includes `subagent` in every SDK and `swarm` or
`graph` where those tools are available. A `call_count` limit therefore caps
each agent rather than the whole delegation tree. To bound the total, also
limit calls to the delegation tools you enable.

## Context structure

Every authorization request includes a structured context object:

```json
{
  "input": { "query": "quarterly report" },
  "session": {
    "hour_utc": 14,
    "call_count": 3,
    "role": "admin"
  }
}
```

- `context.input` contains the tool's input arguments, accessible in policies via `context.input.fieldName`
- `context.session.hour_utc` is auto-populated with the current UTC hour (0-23)
- `context.session.call_count` tracks per-tool invocation count
- Additional `context.session` fields come from your
  <Syntax py="context_enricher" ts="contextEnricher" rs="context_enricher" />

## Error handling

Cedar engine failures (malformed policies, evaluation errors) are always fail-closed: the tool call is denied regardless of configuration.

The <Syntax py="on_error" ts="onError" rs="on_error" /> option controls what
happens when your user-supplied callbacks
(<Syntax py="principal_resolver" ts="principalResolver" rs="principal_resolver" />
or
<Syntax py="context_enricher" ts="contextEnricher" rs="context_enricher" />)
raise an exception:

- `'throw'` (default): re-raises the exception to the caller
- `'deny'`: treats the callback failure as a denial (fail-closed)
- `'proceed'`: allows the tool call despite the callback error (fail-open)

:::caution[Fail-open on callback errors]
With `'proceed'`, any exception from
<Syntax py="principal_resolver" ts="principalResolver" rs="principal_resolver" />
or
<Syntax py="context_enricher" ts="contextEnricher" rs="context_enricher" />
lets the tool call run without a Cedar authorization check. Don't use it when
your agent relies on Cedar to enforce access. To block the tool call instead of
failing the invocation, use `'deny'`.
:::
